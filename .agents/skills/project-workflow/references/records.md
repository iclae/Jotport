# 项目记录格式

这些文件直接可读，辅助脚本只检查格式、来源和写入冲突，不决定业务是否完成。所有路径相对项目根目录；来源摘要使用文件原始字节的 SHA-256。原票、任务事实和主题经验分别维护。

## 执行记录

`.factory/tasks/<id>.json` 示例：

```json
{
  "id": "example",
  "goal": "完成已明确的界面需求",
  "status": "in-progress",
  "ticket": ".scratch/example/issue.md",
  "baselines": [{ "repo": ".", "ref": "实际分支与提交" }],
  "evidence": [{ "path": "实际报告路径", "result": "实际结果与未覆盖项" }],
  "unfinished": ["尚待完成的事项"]
}
```

`id`、`goal`、`status` 必填；其余按需。状态为 `open`、`in-progress`、`blocked`、`done`、`cancelled`。原票可以是路径或 URL。`baselines.repo` 是项目内仓库路径；外部仓库在其项目内另记任务，通过原票关联。需要保留候选发现时，可加 `candidates:[{id,text,sources:["项目内路径"]}]`，不强制每个任务生成经验。

可直接编辑；用辅助工具保存时传入 `{"expectedDigest":null,"task":{...}}`，更新则将 `expectedDigest` 替换为已读取任务文件的摘要。正文保存后的回执位于 `.factory/history/`。记录工具不执行验证命令，结果需要引用实际证据。

证据路径填写项目内可保留的文件。外部回执或临时日志可在项目内留下脱敏摘要，写明对应提交、可重跑的命令及仍能核验的范围；工作区清理后补上归档位置。读取旧任务时，`context` 会略过不符合路径格式的证据项，返回其余任务内容、原文件入口和字段位置。编辑时以原文件为准。能显示相对路径仅表示格式可读，核验结果仍需打开对应产物确认。

### 关键转折与审查证据

按发生顺序在 `evidence` 中追加关键转折，或在已有 Markdown 执行记录里写简短条目。写明当时的假设或尝试、何处被证据推翻、后续动作及验证结果。用日期和票据、提交或检查入口定位该次尝试。已有证据在仓库外时，引用项目内可保留的脱敏摘要，并写明原证据入口和当前可核验范围。

例如，某次尝试假设门店停用后应隐藏历史订单。验收用例要求历史订单仍可查询，因此实现改了查询过滤条件。执行记录引用该用例，并写清改动前失败、改动后通过的结果。此后另一项任务再次出现同类错误时，可以用两份记录核对各自的原因。

独立审查沿用相同证据入口，保留审查者、基线、待交付版本、需求和规则依据、结论及未核实项。复盘可以引用这些记录，说明是否验证了纠正措施，以及是否有后续可比任务观察到收益。

## 主题经验

`.factory/memory/<topic>.md` 使用以下简短头部，后接自由 Markdown 正文：

```markdown
# 主题标题

Status: candidate
Scope: ["src/forms"]
Sources: [{"path":"docs/evidence/example.md","digest":"实际 SHA-256"}]

适用条件、发现、已知例外以及依据。区分已证实的事实与推断。
```

- `candidate`：待验证，只供调查参考。
- `supported`：有来源支持，使用时仍须核对范围；不增加权限。
- `disputed`：存在争议，退出默认建议。
- `stale`：已失效，退出默认建议。

全项目范围用 `["*"]`。来源变化会使主题退出默认建议；重新核对后才更新来源摘要。稳定的原始证据更适合作为来源，持续变化的任务文件须在其变化后重新核对。

手工编辑后，正文立即可读。索引可以直接按现有格式维护，也可运行一次新的空整理重建；不要为了索引重复执行原业务验证。

### 用户确认的约定

显式记忆沿用主题经验格式。正文写清什么时候采用、适用于哪里和何时例外。主题名用后续任务可识别的操作或场景。

优先引用已有的项目内确认来源。仅有会话时，在 `.factory/history/` 留一份最短的确认摘要，写明确认日期、约定及可核对的来源定位。修改约定时保存新的确认来源，保留旧来源供归档主题核对。主题的 `Sources` 引用该文件及其原始字节的 SHA-256。

## 整理输入

当前 agent 核对语义后，可用项目内脚本 `consolidate --input <JSON>` 保存修改：

```json
{
  "id": "review-example-1",
  "sources": [{ "path": "docs/evidence/example.md", "digest": "实际 SHA-256" }],
  "operations": [{
    "op": "upsert",
    "topic": "form-loading",
    "expectedDigest": null,
    "reason": "合并本次同主题发现，结论仍待验证",
    "content": {
      "title": "表单加载经验",
      "status": "candidate",
      "scope": ["src/forms"],
      "sources": ["docs/evidence/example.md"],
      "body": "适用条件、观察结果和待核对事项。"
    }
  }]
}
```

新主题的 `expectedDigest` 为 `null`；修改已有主题须使用读到的原文摘要。归档使用 `{op:"archive",topic,expectedDigest,reason}`，保留旧原文。同一整理 `id` 只对应同一份输入，重跑不会重复添加；新发现或修正使用新的 `id`。任务、主题、整理标识使用字母、数字、点、下划线或连字符。

只重建索引可使用新的 `id`、`sources:[]`、`operations:[]`。并行执行者先留各自候选，由一个整理者提交正式主题修改。进程异常退出时，先确认写入者已退出再处理残留 `.factory/.writer-lock`，保留暂存清单并重跑原请求；工具不会自动抢锁。


## 可恢复性判断（不增加 schema）

沿用主题正文和整理操作的 `reason`，无需新字段或自动分类器。记录足以复核的判断，例如：

- 不新增经验：默认超时可直接查 `src/client.ts`，已有测试覆盖；若业务词难定位，只更新项目导航。
- 保留经验：重试与取消同时发生才触发的失效条件及取舍原因，源码只呈现结果；正文保留条件、反例与原证据。
- 归档重复事实：已核对规范中的来源、权限与适用范围，原主题移入 archive，理由指向替代入口；来源不可访问则不能声称已可恢复。

这些是 agent 的语义判断。`check`/`consolidate` 仍仅负责格式、摘要、冲突与可追溯写入，不证明信息值得丢弃。

## 可选功能导航（项目自有）

优先复用已有导航；没有时可在 `docs/feature-map.md` 使用以下最小模板，并在 `.factory/policy.md` 链接它。不是必装文件，不放在 memory 索引中，不由工具升级覆盖。

```markdown
# 功能导航
仅用于定位。使用前核对当前代码，不作为业务规范或验收结论。

| 业务功能 / 别名 | 最小实现入口 | 规范 / ADR | 相关验证入口 | 核对版本 / 日期 |
| --- | --- | --- | --- | --- |
| 示例功能 / 搜索别名 | src/example.ts（关键符号） | docs/spec.md#section | tests/example.test.mjs | <commit> / YYYY-MM-DD |
```

路径以项目根目录为基准；入口只选定位必需的少数文件。没有规范或测试如实写“未有”，不要虚构。变更时按触及范围维护；失效回到源码/搜索。仅检查存在不等于语义映射正确。工具仓提供约定，真实条目、证据和业务词属于项目仓。

## 轻量收益评估（项目自有、可选）

不要求旧版 release 协议或常驻评估服务。项目在自己的 `docs/evaluation/` 或已有评估目录保存计划、隔离输入和结果；不把业务原文带回工具仓。

1. **冻结计划与验收**：先选择 4–6 个代表任务（接续、纠错、常规修改及无关经验负例），保存起始 commit、任务输入、隐藏的独立验收条件、预算和成本口径。不能在看到结果后改通过标准。
2. **经验三组**：A 无经验；B 现有经验；C 可恢复性筛选后经验。仅经验暴露不同；代码/文档/导航、模型版本、工具权限、token/时间预算相同。每组每题使用独立干净会话与工作区，不能读取其他组的产物或任务解答。固定起始快照，运行间不反哺新记忆。
3. **防泄漏**：验收答案、历史解法、其他组记录与输出放在执行者不可读位置；检查 policy/任务记录/上下文也没有残留答案。三组使用同一任务专用启动入口，仅改变经验加载，A 不可通过普通搜索偷读被禁经验。做不到隔离时标注无效，不宣称因果收益。
4. **导航单独比较**：另选 2–3 个难定位任务，保持同一经验快照，比较普通搜索与搜索加导航。不要把导航的定位收益记成经验收益。
5. **执行与裁判分离**：独立按预先验收检查最终改动，而不是采信 agent 的完成声明。记录成功、回归/无关修改、虚假完成、人工介入与返工，以及耗时/token。失败和中止同样保留。
6. **成本与结论**：任务执行、记忆提取/整理/检索、导航维护都计入运行成本；一次性建设成本单列并说明摊销任务数，评估实验成本另列。先运行 12–18 次作筛查，不作统计显著性结论；有价值才安排留出任务和重复验证。没有真实模型任务运行时，只能说方法/机制准备完成。

计划最少记录：任务 ID、起始 commit、各输入摘要、模型/工具/预算、允许读取边界、独立验收位置、运行顺序、预先约定的保留/停止条件。按任务配对比较，不能仅比较总平均或记忆条数。

结果表可复制：

| 任务 / 组 / 重复 | 起始 commit / 输入摘要 | 独立验收及证据 | 回归 / 无关修改 / 虚假完成 | 人工介入 / 返工 | 执行时间 / token | 提取整理检索 / 导航维护成本 | 有效性 / 限制 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待运行 | 待冻结 | 未验证 | 未测 | 未测 | 未测 | 未测 | 不推断收益 |

试点报告必须区分：工程机制检查、实际任务完成情况、经验效果、导航效果。若质量退化或维护成本抵消节省，缩小范围或停用，不为保留记忆系统找理由。
